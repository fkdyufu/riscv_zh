第 1 章 操作系统接口

操作系统的工作是在多个程序之间共享一台计算机，并提供一组比硬件本身更有用的服务。操作系统管理并抽象底层硬件，例如，文字处理器不必关心正在使用哪种磁盘硬件。操作系统在多个程序之间共享硬件，使它们同时运行（或看起来同时运行）。最后，操作系统为程序之间的交互提供受控方式，使它们能够共享数据或协同工作。

操作系统通过一个接口向用户程序提供服务。设计一个好的接口并不容易。一方面，我们希望接口简单而狭窄，因为这样更容易把实现做正确。另一方面，我们可能又想向应用程序提供许多复杂的功能。解决这种张力的诀窍，是设计依赖少数机制的接口，而这些机制可以组合起来提供很强的通用性。

本书使用一个具体的操作系统作为示例来说明操作系统概念。这个操作系统就是 xv6，它提供了 Ken Thompson 和 Dennis Ritchie 的 Unix 操作系统 [17] 引入的基本接口，同时也模仿 Unix 的内部设计。Unix 提供了一个狭窄的接口，其中的机制能够很好地组合，展现出令人惊讶的通用性。这个接口非常成功，以至于现代操作系统——BSD、Linux、macOS、Solaris，甚至在较小程度上包括 Microsoft Windows——都具有类 Unix 接口。理解 xv6，是理解这些系统以及许多其他系统的良好起点。

如图 1.1所示，xv6 采用传统的内核形式：内核是一个特殊程序，为正在运行的程序提供服务。每个正在运行的程序称为一个进程，它拥有包含指令、数据和栈的内存。指令实现程序的计算；数据是计算所作用的变量；栈组织程序的过程调用。一台给定的计算机通常有许多进程，但只有一个内核。

当进程需要调用内核服务时，它会发起系统调用，也就是操作系统接口中的一种调用。系统调用进入内核；内核执行相应服务并返回。因此，一个进程会在用户空间和内核空间之间交替执行。

后续章节会详细说明，内核使用 CPU1 提供的硬件保护机制，确保每个在用户空间执行的进程只能访问自己的内存。内核以实现这些保护所需的硬件特权执行；用户程序则在没有这些特权的情况下执行。当用户程序发起系统调用时，硬件会提升特权级，并开始执行内核中预先安排好的函数。

内核提供的系统调用集合，就是用户程序所看到的接口。xv6 内核提供了 Unix 内核传统上提供的服务和系统调用的一个子集。图 1.2列出了 xv6 的全部系统调用。

本章余下部分概述 xv6 的服务——进程、内存、文件描述符、管道和文件系统——并通过代码片段以及对 shell（Unix 的命令行用户接口）如何使用它们的讨论来说明这些服务。shell 对系统调用的使用展示了这些调用经过了多么谨慎的设计。

shell 是一个普通程序，它读取用户输入的命令并执行这些命令。shell 是用户程序而不是内核的一部分，这一点体现了系统调用接口的力量：shell 并没有什么特殊之处。这也意味着 shell 很容易被替换；因此，现代 Unix 系统有多种 shell 可供选择，每种 shell 都有自己的用户接口和脚本功能。xv6 shell 是对 Unix Bourne shell 精髓的一个简单实现。

xv6 shell 的实现可以在 (7850) 找到。（该链接是指向相关 xv6 源代码的超链接：https://github.com/mit-pdos/xv6-riscv/；具体数字指的是 xv6-src-booklet.pdf 中的页片和行号，其方式类似 Lions 的 Commentary on UNIX 6th Edition [11]。一个好的做法是先自己阅读源代码（使用你喜欢的开发环境、GitHub 或 PDF 阅读器），然后再回到本书。读完本书后，你应该能够不查阅本书就理解 xv6 源代码的每一行。）

1.1 进程和内存

一个 xv6 进程由用户空间内存（指令、数据和栈）以及内核中该进程私有的状态组成。Xv6 对进程进行时间共享：它在等待执行的进程集合之间透明地切换可用的 CPU。当一个进程没有执行时，xv6 会保存该进程的 CPU 寄存器，并在下次运行该进程时恢复它们。内核为每个进程关联一个进程标识符，即 PID。

进程可以使用 fork 系统调用创建一个新进程。fork 为新进程提供调用进程内存的精确副本：它把调用进程的指令、数据和栈复制到新进程的内存中。fork 会在原进程和新进程中都返回。在原进程中，fork 返回新进程的 PID；在新进程中，fork 返回零。原进程和新进程通常分别称为父进程和子进程。

例如，考虑下面这段用 C 语言 [7] 编写的程序片段：

int pid = fork();
if(pid > 0){
  printf("parent: child=%d\n", pid);
  pid = wait((int *) 0);
  printf("child %d is done\n", pid);
} else if(pid == 0){
  printf("child: exiting\n");
  exit(0);
} else {
  printf("fork error\n");
}

exit 系统调用使调用进程停止执行，并释放内存和打开文件等资源。exit 接受一个整数状态参数，按惯例 0 表示成功，1 表示失败。wait 系统调用返回当前进程某个已退出（或被杀死）子进程的 PID，并把该子进程的退出状态复制到传给 wait 的地址；如果调用者的子进程都还没有退出，wait 会等待其中一个退出。如果调用者没有子进程，wait 会立即返回 -1。如果父进程不关心子进程的退出状态，可以向 wait 传入地址 0。

在这个例子中，下面两行输出可能以任意顺序出现（甚至可能交错），这取决于父进程和子进程谁先执行到自己的 printf 调用：

parent: child=1234
child: exiting

子进程退出后，父进程的 wait 返回，使父进程打印：

parent: child 1234 is done

虽然子进程开始时拥有父进程内存的一份副本，但父进程和子进程使用相互独立的内存和寄存器执行：在一个进程中修改变量不会影响另一个进程。例如，当父进程把 wait 的返回值存入变量 pid 时，它不会改变子进程中的 pid 变量。子进程中的 pid 值仍然是零。

exec 系统调用会用一个从文件系统中的文件加载的新内存映像替换调用进程的内存。该文件必须具有特定格式，说明文件的哪一部分保存指令、哪一部分是数据、从哪条指令开始执行，等等。Xv6 使用 ELF 格式，第 3 章会更详细地讨论它。通常，这个文件是编译程序源代码的结果。当 exec 成功时，它不会返回到调用程序；相反，从文件加载的指令会从 ELF 头声明的入口点开始执行。exec 接受两个参数：包含可执行程序的文件名，以及字符串参数数组。例如：

char *argv[3];

argv[0] = "echo";
argv[1] = "hello";
argv[2] = 0;
exec("/bin/echo", argv);
printf("exec error\n");

这段代码把调用程序替换为带参数列表 echo hello 运行的 /bin/echo 程序实例。大多数程序会忽略参数数组的第一个元素；按惯例，它是程序名。

xv6 shell 使用上述调用代表用户运行程序。shell 的主体结构很简单；见 (8001)。主循环用 getcmd 从用户读取一行输入，然后调用 fork 创建 shell 进程的副本。父进程调用 wait，子进程运行命令。例如，如果用户在 shell 中输入了 “echo hello”，那么 runcmd 会以 “echo hello” 作为参数被调用。runcmd (7903) 运行实际命令。对于 “echo hello”，它会调用 exec (7927)。如果 exec 成功，那么子进程将执行来自 echo 的指令，而不是来自 runcmd 的指令。在某个时刻，echo 会调用 exit，这会使父进程从 main (8001) 中的 wait 返回。

你可能会疑惑为什么不把 fork 和 exec 合并成一个调用；稍后我们会看到，shell 在实现 I/O 重定向时利用了二者的分离。为了避免创建重复进程后又立刻替换它（用 exec）所造成的浪费，操作系统内核会针对这种使用方式优化 fork 的实现，例如使用写时复制等虚拟内存技术（见第 5 章）。

Xv6 隐式地分配大部分用户空间内存：fork 分配子进程复制父进程内存所需的内存，exec 分配足以容纳可执行文件的内存。运行时需要更多内存的进程（例如为了 malloc）可以调用 sbrk(n)，把自己的数据内存增长 n 个零字节；sbrk 返回新内存的位置。

1.2 I/O 和文件描述符

文件描述符是一个小整数，代表由内核管理、进程可以读取或写入的对象。进程可以通过打开文件、目录或设备，通过创建管道，或者通过复制已有描述符来获得文件描述符。为简单起见，我们常把文件描述符所指向的对象称为“文件”；文件描述符接口抽象掉了文件、管道和设备之间的差异，使它们看起来都像字节流。我们把输入和输出称为 I/O。

在内部，xv6 内核把文件描述符用作进程私有表的索引，因此每个进程都有一个从零开始的私有文件描述符空间。按照惯例，进程从文件描述符 0（标准输入）读取，向文件描述符 1（标准输出）写输出，向文件描述符 2（标准错误）写错误消息。正如我们将看到的，shell 利用这个惯例来实现 I/O 重定向和管道。shell 确保自己总是打开三个文件描述符 (8007)，默认情况下它们都是控制台的文件描述符。

read 和 write 系统调用从由文件描述符命名的打开文件中读取字节，或向其写入字节。调用 read(fd, buf, n) 最多从文件描述符 fd 读取 n 个字节，把它们复制到 buf 中，并返回读取到的字节数。每个指向文件的文件描述符都有一个与之关联的偏移量。read 从当前文件偏移处读取数据，然后把偏移量前移读取的字节数：随后的 read 会返回第一次 read 返回内容之后的字节。当没有更多字节可读时，read 返回零，表示文件结束。

调用 write(fd, buf, n) 从 buf 向文件描述符 fd 写入 n 个字节，并返回写入的字节数。只有发生错误时，写入的字节数才会少于 n。和 read 一样，write 在当前文件偏移处写入数据，然后把偏移量前移写入的字节数：每次 write 都从上一次结束的位置继续。

下面的程序片段（它构成程序 cat 的核心）把标准输入的数据复制到标准输出。如果发生错误，它会向标准错误写一条消息。

char buf[512];
int n;

for(;;){
  n = read(0, buf, sizeof buf);
  if(n == 0)
    break;
  if(n < 0){
    fprintf(2, "read error\n");
    exit(1);
  }
  if(write(1, buf, n) != n){
    fprintf(2, "write error\n");
    exit(1);
  }
}

这段代码中重要的一点是，cat 不知道自己是在从文件、控制台还是管道读取。同样，cat 也不知道自己是在向控制台、文件或其他什么对象打印。文件描述符的使用，以及文件描述符 0 是输入、文件描述符 1 是输出这一惯例，使得 cat 的实现可以很简单。

close 系统调用释放一个文件描述符，使它可以被将来的 open、pipe 或 dup 系统调用（见下文）重用。新分配的文件描述符总是当前进程中编号最小的未使用描述符。

文件描述符和 fork 相互配合，使 I/O 重定向易于实现。fork 会在复制父进程内存的同时复制父进程的文件描述符表，因此子进程一开始拥有与父进程完全相同的打开文件。系统调用 exec 会替换调用进程的内存，但保留它的文件表。这种行为允许 shell 通过以下方式实现 I/O 重定向：先 fork，然后在子进程中关闭并重新打开选定的文件描述符，最后调用 exec 运行新程序。下面是 shell 为命令 cat < input.txt 运行的代码的简化版本：

char *argv[2];

argv[0] = "cat";
argv[1] = 0;
if(fork() == 0) {
  close(0);
  open("input.txt", O_RDONLY);
  exec("cat", argv);
}

子进程关闭文件描述符 0 后，open 保证会把这个文件描述符用于新打开的 input.txt：0 将是最小的可用文件描述符。随后 cat 执行时，文件描述符 0（标准输入）指向 input.txt。这一序列不会改变父进程的文件描述符，因为它只修改了子进程的描述符。

xv6 shell 中的 I/O 重定向代码正是这样工作的 (7931)。回忆一下，在这段代码执行时，shell 已经 fork 出子 shell，而 runcmd 会调用 exec 来加载新程序。

open 的第二个参数由一组以位表示的标志组成，用来控制 open 的行为。可能的取值定义在文件控制（fcntl）头文件中 (4000-4004)：O_RDONLY、O_WRONLY、O_RDWR、O_CREATE 和 O_TRUNC，它们分别指示 open 以只读、只写、读写方式打开文件，在文件不存在时创建文件，以及把文件截断为零长度。

现在应该可以看清为什么把 fork 和 exec 分成两个调用是有帮助的：在两者之间，shell 有机会重定向子进程的 I/O，而不会扰乱主 shell 的 I/O 设置。也可以想象一种假设的合并调用 forkexec，但用这种调用来做 I/O 重定向的选择看起来都很笨拙。shell 可以在调用 forkexec 之前修改自己的 I/O 设置（然后撤销这些修改）；或者 forkexec 可以把 I/O 重定向指令作为参数；或者（最不吸引人的方式）让每个像 cat 这样的程序都学会处理自己的 I/O 重定向。

虽然 fork 会复制文件描述符表，但每个底层文件偏移量会在父子进程之间共享。考虑这个例子：

if(fork() == 0) {
  write(1, "hello ", 6);
  exit(0);
} else {
  wait(0);
  write(1, "world\n", 6);
}

这段代码结束时，连接到文件描述符 1 的文件将包含数据 hello world。父进程中的 write（由于 wait，它只在子进程完成后运行）会从子进程的 write 停止的位置继续。这种行为有助于从 shell 命令序列产生顺序输出，例如 (echo hello; echo world) >output.txt。

dup 系统调用复制一个已有的文件描述符，返回一个新的文件描述符，指向同一个底层 I/O 对象。两个文件描述符共享一个偏移量，就像由 fork 复制出的文件描述符那样。下面是另一种把 hello world 写入文件的方法：

fd = dup(1);
write(1, "hello ", 6);
write(fd, "world\n", 6);

如果两个文件描述符是通过一系列 fork 和 dup 调用从同一个原始文件描述符派生出来的，它们就共享偏移量。否则，即使它们来自对同一文件的 open 调用，文件描述符也不共享偏移量。dup 允许 shell 实现这样的命令：ls existing-file non-existing-file > tmp1 2>&1。2>&1 告诉 shell 给该命令一个文件描述符 2，它是描述符 1 的副本。已有文件的名字和不存在文件的错误消息都会出现在文件 tmp1 中。xv6 shell 不支持错误文件描述符的 I/O 重定向，但现在你已经知道如何实现它。

文件描述符是一种强大的抽象，因为它们隐藏了自己连接到的对象的细节：向文件描述符 1 写入的进程，可能是在写一个文件、像控制台这样的设备，或者一个管道。

1.3 管道

管道是一个小的内核缓冲区，以一对文件描述符的形式暴露给进程，一个用于读取，一个用于写入。向管道的一端写入数据，会使这些数据可以从管道的另一端读出。管道为进程之间通信提供了一种方式。

下面的示例代码运行程序 wc，并把它的标准输入连接到管道的读端。

int p[2];
char *argv[2];

argv[0] = "wc";
argv[1] = 0;

pipe(p);
if(fork() == 0) {
  close(0);
  dup(p[0]);
  close(p[0]);
  close(p[1]);
  exec("/bin/wc", argv);
} else {
  close(p[0]);
  write(p[1], "hello world\n", 12);
  close(p[1]);
}

程序调用 pipe，它创建一个新管道，并把读、写文件描述符记录在数组 p 中。fork 之后，父进程和子进程都有指向该管道的文件描述符。子进程调用 close 和 dup，使文件描述符 0 指向管道的读端，关闭 p 中的文件描述符，并调用 exec 运行 wc。当 wc 从标准输入读取时，它从管道读取。父进程关闭管道的读端，向管道写入，然后关闭写端。

如果没有可用数据，对管道的 read 会等待，直到有数据被写入，或者所有指向写端的文件描述符都被关闭；后一种情况下，read 会返回 0，就像已经到达数据文件的末尾一样。read 会阻塞直到新数据不可能再到达，这也是上面代码中子进程在执行 wc 前关闭管道写端的重要原因之一：如果 wc 的某个文件描述符仍指向管道写端，wc 就永远看不到文件结束。

xv6 shell 以类似上面代码的方式实现形如 grep fork sh.c | wc -l 的管道线 (7950)。子进程创建一个管道，把管道线左端连接到右端。然后它为管道线左端调用 fork 和 runcmd，为右端也调用 fork 和 runcmd，并等待二者完成。管道线右端可能本身又是一个包含管道的命令（例如 a | b | c），它又会 fork 出两个新的子进程（一个用于 b，一个用于 c）。因此，shell 可能创建一棵进程树。这棵树的叶子是命令，内部节点则是等待左、右子进程完成的进程。

管道看起来似乎并不比临时文件更强大：管道线

echo hello world | wc

可以不用管道实现为：

echo hello world >/tmp/xyz; wc </tmp/xyz

在这种情况下，管道相对于临时文件至少有三个优点。第一，管道会自动清理自身；而使用文件重定向时，shell 必须小心地在完成后删除 /tmp/xyz。第二，管道可以传递任意长的数据流，而文件重定向需要磁盘上有足够的空闲空间来保存全部数据。第三，管道允许管道线各阶段并行执行，而文件方式要求第一个程序完成后第二个程序才能开始。

1.4 文件系统

xv6 文件系统提供数据文件和目录。数据文件包含未解释的字节数组；目录包含对数据文件和其他目录的具名引用。目录形成一棵树，从一个称为根目录的特殊目录开始。像 /a/b/c 这样的路径，指的是根目录 / 中名为 a 的目录内，名为 b 的目录内，名为 c 的文件或目录。不以 / 开头的路径，会相对于调用进程的当前目录求值；当前目录可以通过 chdir 系统调用改变。下面两个代码片段打开同一个文件（假设涉及的所有目录都存在）：

chdir("/a");
chdir("b");
open("c", O_RDONLY);

open("/a/b/c", O_RDONLY);

第一个片段把进程的当前目录改为 /a/b；第二个片段既不引用也不改变进程的当前目录。

有一些系统调用用于创建新文件和目录：mkdir 创建新目录，带 O_CREATE 标志的 open 创建新的数据文件，mknod 创建新的设备文件。下面的例子说明了这三者：

mkdir("/dir");
fd = open("/dir/file", O_CREATE|O_WRONLY);
close(fd);
mknod("/console", 1, 1);

mknod 创建一个指向设备的特殊文件。设备文件关联着主设备号和次设备号（mknod 的两个参数），它们唯一标识一个内核设备。当进程稍后打开设备文件时，内核会把 read 和 write 系统调用转交给内核设备实现，而不是传给文件系统。

文件名与文件本身是不同的；同一个底层文件，称为 inode，可以有多个名字，称为链接。每个链接都是目录中的一个条目；该条目包含一个文件名和一个对 inode 的引用。inode 保存文件的元数据，包括它的类型（文件、目录或设备）、长度、文件内容在磁盘上的位置，以及指向该文件的链接数量。

fstat 系统调用从文件描述符所指向的 inode 中取回信息。它会填充一个 struct stat，该结构在 stat.h (4050) 中定义如下：

#define T_DIR     1   // Directory
#define T_FILE    2   // File
#define T_DEVICE  3   // Device

struct stat {
  int dev;      // File system's disk device
  uint ino;     // Inode number
  short type;   // Type of file
  short nlink;  // Number of links to file
  uint64 size;  // Size of file in bytes
};

link 系统调用创建另一个文件系统名字，使它指向与已有文件相同的 inode。下面的片段创建一个同时名为 a 和 b 的新文件。

open("a", O_CREATE|O_WRONLY);
link("a", "b");

从 a 读取或向 a 写入，与从 b 读取或向 b 写入是一样的。每个 inode 都由唯一的 inode 编号标识。执行上面的代码序列后，可以通过检查 fstat 的结果确定 a 和 b 指向同一底层内容：二者会返回相同的 inode 编号（ino），并且 nlink 计数会被设为 2。

unlink 系统调用从文件系统中移除一个名字。只有当文件的链接计数为零，并且没有文件描述符引用它时，文件的 inode 和保存其内容的磁盘空间才会被释放。因此，在上一段代码序列后添加：

unlink("a");

仍然会留下可以通过 b 访问的 inode 和文件内容。此外，

fd = open("/tmp/xyz", O_CREATE|O_RDWR);
unlink("/tmp/xyz");

是一种惯用方式，用来创建一个没有名字的临时 inode；当进程关闭 fd 或退出时，它会被清理。

Unix 提供了可以从 shell 调用的用户级文件工具，例如 mkdir、ln 和 rm。这种设计允许任何人通过添加新的用户级程序来扩展命令行接口。事后看来这个方案似乎显而易见，但与 Unix 同时代设计的其他系统，常常把这类命令内建到 shell 中（并把 shell 内建到内核中）。

一个例外是 cd，它内建在 shell 中 (8021)。cd 必须改变 shell 自身的当前工作目录。如果把 cd 作为普通命令运行，那么 shell 会 fork 一个子进程，子进程运行 cd，而 cd 会改变子进程的工作目录。父进程（也就是 shell）的工作目录不会改变。

1.5 现实世界

Unix 将“标准”文件描述符、管道以及用于操作它们的便捷 shell 语法结合起来，这是编写通用可复用程序的一项重大进步。这个想法催生了“软件工具”文化，而这种文化在很大程度上造就了 Unix 的力量和流行；shell 则是第一个所谓的“脚本语言”。Unix 系统调用接口至今仍存在于 BSD、Linux 和 macOS 等系统中。

Unix 系统调用接口已经通过可移植操作系统接口（Portable Operating System Interface，POSIX）标准化。Xv6 并不符合 POSIX：它缺少许多系统调用（包括像 lseek 这样的基本调用），并且它提供的许多系统调用与标准不同。我们设计 xv6 的主要目标是在提供一个简单的类 UNIX 系统调用接口的同时，保持简单和清晰。已经有一些人给 xv6 扩展了少量系统调用和一个简单的 C 库，以便运行基本的 Unix 程序。然而，现代内核提供的系统调用和内核服务种类都比 xv6 多得多。例如，它们支持网络、窗口系统、用户级线程、许多设备的驱动程序，等等。现代内核持续而快速地演化，并提供许多超出 POSIX 的功能。

Unix 用一组统一的文件名和文件描述符接口，统一了对多种资源（文件、目录和设备）的访问。这个想法可以扩展到更多种资源；Plan 9 [16] 是一个很好的例子，它把“资源都是文件”的概念应用到网络、图形以及更多对象上。然而，大多数源自 Unix 的操作系统并没有沿着这条路线发展。

文件系统和文件描述符一直是强大的抽象。即便如此，操作系统接口还有其他模型。Unix 的前身 Multics 以一种让文件存储看起来像内存的方式来抽象文件存储，由此产生了一种非常不同风格的接口。Multics 设计的复杂性直接影响了 Unix 的设计者，他们的目标是构建一个更简单的东西。

Xv6 没有用户的概念，也没有保护一个用户不受另一个用户影响的机制；用 Unix 术语来说，所有 xv6 进程都以 root 身份运行。

本书考察 xv6 如何实现其类 Unix 接口，但这些思想和概念并不只适用于 Unix。任何操作系统都必须把多个进程复用到底层硬件上，使进程彼此隔离，并提供受控的进程间通信机制。学习 xv6 之后，你应该能够观察其他更复杂的操作系统，并在其中看到 xv6 背后的那些概念。
