第 11 章 重谈并发

在内核设计中，同时获得良好的并行性能、并发下的正确性，以及容易理解的代码，是一个很大的挑战。直接使用锁是通向正确性的最好路径，但并不总是可行。本章重点展示一些例子：xv6 被迫以复杂方式使用锁的地方，以及 xv6 使用类似锁的技术但并没有真正使用锁的地方。

11.1 加锁模式

缓存项通常很难加锁。例如，文件系统的块缓存 (4275) 保存最多 NBUF 个磁盘块的副本。某个给定磁盘块在缓存中最多只能有一份副本，这一点至关重要；否则，不同进程可能会对本应是同一个块的不同副本做出相互冲突的修改。每个缓存块保存在一个 struct buf 中 (3900)。struct buf 有一个 lock 字段，用于帮助确保同一时刻只有一个进程使用某个给定磁盘块。不过，仅有这把锁还不够：如果某个块根本不在缓存中，而两个进程同时想使用它，会怎么样？此时没有 struct buf（因为该块还没有被缓存），因此也没有东西可锁。xv6 通过把另一把锁（bcache.lock）关联到“已缓存块的身份集合”来处理这种情况。需要检查某个块是否已缓存（例如 bget (4308)），或者改变已缓存块集合的代码，必须持有 bcache.lock；随后，代码找到所需块和 struct buf 后，就可以释放 bcache.lock，只锁住那个具体块。这是一种常见模式：集合一把锁，每个项再一把锁。

通常，获取锁的函数也会释放锁。但更精确的看法是：锁在一段必须表现为原子的序列开始处获取，在该序列结束时释放。如果序列在不同函数、不同线程或不同 CPU 上开始和结束，那么获取锁和释放锁也必须这样分开。锁的功能是强制其他使用者等待，而不是把某份数据固定到某个特定执行者上。一个例子是 yield 中的 acquire (2629)，它由调度器线程释放，而不是由获取它的进程释放。另一个例子是 ilock 中的 acquiresleep (5153)；这段代码在读磁盘时经常睡眠，醒来时可能在另一个 CPU 上，这意味着锁可能在不同 CPU 上获取和释放。

释放一个受嵌入对象内部锁保护的对象，是一件微妙的事，因为拥有这把锁并不足以保证释放该对象是正确的。问题场景是：另一个线程正在 acquire 中等待使用这个对象；释放对象会隐式释放其中嵌入的锁，从而让等待线程出错。一种解决方案是跟踪对象有多少引用，只有最后一个引用消失时才释放对象。pipeclose (6661) 就是一个例子；pi->readopen 和 pi->writeopen 跟踪是否还有文件描述符引用该管道。

人们通常会在一组相关项的读写序列周围看到锁；锁保证其他线程只看到完整的更新序列（只要它们也加锁）。那如果更新只是对单个共享变量的一次简单写入呢？例如，setkilled 和 killed (2775) 会围绕对 p->killed 的简单使用加锁。如果没有锁，一个线程可能在另一个线程读取 p->killed 的同时写它。这是竞争，而 C 语言规范规定竞争会导致未定义行为，这意味着程序可能崩溃，或产生错误结果1。锁防止竞争，并避免未定义行为。

竞争会破坏程序的一个原因是，如果没有锁或等价构造，编译器可能生成与原始 C 代码非常不同的读写内存机器码。例如，调用 killed 的线程的机器码可能把 p->killed 复制到寄存器中，然后只读取这个缓存值；这意味着该线程可能永远看不到任何对 p->killed 的写入。锁会防止这种缓存。

11.2 类锁模式

在许多地方，xv6 用引用计数或标志以类似锁的方式表示某个对象已经分配，不应被释放或复用。进程的 p->state 以这种方式工作，file、inode 和 buf 结构中的引用计数也是如此。虽然每种情况下都有一把锁保护标志或引用计数，但真正防止对象过早释放的是标志或引用计数本身。

文件系统把 struct inode 的引用计数用作一种可由多个进程持有的共享锁，以避免如果使用普通锁会发生的死锁。例如，namex 中的循环 (5555) 会依次锁住每个路径名组件命名的目录。不过，namex 必须在循环末尾释放每把锁，因为如果它持有多把锁，当路径名包含点（例如 a/./b）时，它可能与自己死锁。它也可能与涉及该目录和 .. 的并发查找死锁。如第 10 章所解释，解决方案是让循环把目录 inode 带到下一次迭代时递增其引用计数，但不保持锁定。

有些数据项在不同时间由不同机制保护，有时还会由 xv6 代码结构隐式保护，免受并发访问，而不是由显式锁保护。例如，当一个物理页空闲时，它由 kmem.lock 保护 (2973)。如果该页随后被分配为管道 (6622)，它由另一把锁保护（嵌入的 pi->lock）。如果该页被重新分配为新进程的用户内存，它根本不由锁保护。相反，分配器不会把该页给任何其他进程（直到它被释放），这一事实保护它免受并发访问。新进程内存的所有权很复杂：首先父进程在 fork 中分配并操作它，然后子进程使用它，子进程退出后父进程再次拥有这块内存并把它传给 kfree。这里有两个教训：一个数据对象在其生命周期的不同阶段可能以不同方式受并发保护；这种保护可能表现为隐式结构，而不是显式锁。

最后一个类锁例子是，在调用 mycpu() 前后需要禁用中断 (2187)。禁用中断使调用代码相对于定时器中断成为原子的；定时器中断可能强制上下文切换，从而把进程移到另一个 CPU。

11.3 完全不用锁

xv6 有少数地方在完全没有锁的情况下共享可变数据。一个例子是自旋锁实现内部，尽管也可以把 RISC-V 原子指令看作依赖硬件实现的锁。另一个例子是 main.c 中的 started 变量 (1156)，它用于阻止其他 CPU 运行，直到 CPU zero 完成 xv6 初始化；volatile 确保编译器确实生成 load 和 store 指令。

xv6 包含这样的情况：一个 CPU 或线程写入某些数据，另一个 CPU 或线程读取这些数据，但没有专门保护这些数据的特定锁。例如，在 fork 中，父进程写子进程的用户内存页，而子进程（另一个线程，可能在另一个 CPU 上）读取这些页；没有锁显式保护这些页。严格来说这不是锁问题，因为父进程写完之前子进程不会开始执行。它是一个潜在的内存顺序问题（见第 7 章），因为如果没有内存屏障，没有理由期望一个 CPU 会看到另一个 CPU 的写入。不过，由于父进程会释放锁，而子进程启动时会获取锁，acquire 和 release 中的内存屏障确保子进程所在 CPU 能看到父进程的写入。

11.4 并行性

加锁主要是为了正确性而抑制并行性。由于性能也很重要，内核设计者经常必须思考如何使用锁，既实现正确性，又允许并行性。虽然 xv6 没有系统性地为高性能设计，但仍值得考虑 xv6 中哪些操作可以并行执行，哪些操作可能在锁上冲突。

xv6 中的管道是并行性相当不错的例子。每个管道有自己的锁，因此不同进程可以在不同 CPU 上并行读写不同管道。不过，对于某个给定管道，写者和读者必须等待对方释放锁；它们不能同时读写同一个管道。从空管道读取（或向满管道写入）也必须阻塞，但这并不是加锁方案造成的。

上下文切换是一个更复杂的例子。两个内核线程各自在自己的 CPU 上执行时，可以同时调用 yield、sched 和 swtch，这些调用会并行执行。每个线程都持有一把锁，但它们是不同的锁，所以不必互相等待。不过，一旦进入 scheduler，两个 CPU 在搜索进程表以寻找 RUNNABLE 进程时，可能会在锁上冲突。也就是说，xv6 很可能能在上下文切换期间从多个 CPU 获得性能收益，但收益也许没有本可以达到的那么多。

另一个例子是不同 CPU 上的不同进程并发调用 fork。这些调用可能必须为 pid_lock、kmem.lock，以及搜索进程表中 UNUSED 进程所需的每进程锁而互相等待。另一方面，两个正在 fork 的进程可以完全并行地复制用户内存页并格式化页表页。

上述每个例子中的加锁方案都在某些情况下牺牲了并行性能。每种情况都可以通过更复杂的设计获得更多并行性。是否值得这样做取决于细节：相关操作调用频率有多高，代码在有争用锁上持锁多久，可能同时运行冲突操作的 CPU 有多少，以及代码其他部分是否存在更严格的瓶颈。很难猜测某个给定加锁方案是否会造成性能问题，也很难猜测新设计是否显著更好，因此通常需要在真实工作负载上测量。

11.5 练习

  1. 修改 xv6 的管道实现，使对同一个管道的一次读和一次写可以在不同 CPU 上并行进行。
  2. 修改 xv6 的 scheduler()，以减少不同 CPU 同时寻找可运行进程时的锁争用。
  3. 消除 xv6 的 fork() 中的一些串行化。
